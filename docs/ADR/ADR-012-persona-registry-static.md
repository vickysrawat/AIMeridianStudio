# ADR-012 — Persona Registry as Static; Tone/Goal/Criteria as Dynamic

**Status:** Accepted
**Date:** June 2026
**Deciders:** MeridianStudio team

## Context

For goal-directed document generation, three distinct pieces of context drive the LLM system prompt:
1. **Persona** — who is writing this document (e.g., Account Executive / Partner)
2. **Tone** — how it should sound (e.g., commercial and persuasive)
3. **Goal** — what the document must achieve
4. **Criteria** — how to evaluate whether the goal was achieved

The question was which of these should be static (hardcoded per template type) and which should be dynamic (LLM-generated per request).

An early design made all four static in `MissionRegistry`. This was rejected because tone/goal/criteria vary meaningfully by domain and solution type — the same template type used for a healthcare compliance proposal needs different options than for a retail e-commerce proposal (see ADR-009).

The persona, however, was considered separately. An "Account Executive / Partner" writing a proposal is a stable relationship — it does not change based on whether the domain is healthcare or retail. The persona is the voice of the document, not its subject matter.

## Decision

**`PersonaRegistry`** (`Infrastructure/LLM/PersonaRegistry.cs`) is a **static class** that maps each of the 7 template types to exactly two stable fields:
- `Persona` — who is producing the document (e.g., "Account Executive / Partner")
- `SecondaryAudience` — who else reads it (e.g., "Sr. Delivery Manager, Client Sponsor")

These fields are:
- The same regardless of domain, solution type, or user preferences
- Loaded immediately (no LLM call) when the UI selects a template type
- Used in the system prompt as the fundamental identity of the document author

**Tone, goal, and criteria** are **never stored in `PersonaRegistry`**. They are generated by `MissionSuggestionService` per request (ADR-009) and selected/refined by the user before generation.

This split means:
- The persona chip in the Document Studio UI renders instantly (no API wait)
- The tone/goal/criteria panels show skeleton loading while `POST /api/mission-suggestions` responds
- The system prompt always knows who is writing; it waits for user selection to know how and why

The `DocumentMission` record (assembled just before generation) carries all four fields together: `Persona` (from registry) + `SelectedTone + SelectedGoal + SelectedCriteria` (from user selection).

## Consequences

### Positive
- Persona is always available — the "Writing as: Account Executive / Partner" chip in the UI renders instantly without an API call, giving users immediate orientation
- Stable persona means the fundamental author identity is not subject to LLM drift or hallucination
- Clean separation of concerns: registry owns identity; suggestions service owns context-specific content
- Extending to a new template type requires only one entry in `PersonaRegistry` (two fields) — the LLM handles the rest contextually

### Negative / Trade-offs
- The persona is prescriptive — if a user wants to generate a proposal "thinking like a Technical Architect" instead of an "Account Executive", there is no mechanism to override the persona (unlike tone/goal/criteria which are all user-overridable)
- The 7-persona list is hardcoded — adding a new template type requires a code change to `PersonaRegistry`
- Secondary audience is also static — a highly specific use case (e.g., "proposal for a regulated NHS trust") might benefit from a dynamically tailored secondary audience description

### Failure Modes
- The `PersonaRegistry._default` fallback returns `("Senior Consultant", "Executive Stakeholders")` for unrecognised template types. If a new template type is added without a `PersonaRegistry` entry, the document will be produced with a generic persona — functional but not optimal.
- The persona is injected into the LLM system prompt as a string. A persona name that contains special characters or is excessively long could cause prompt formatting issues in raw-string literals — mitigated by the controlled, short strings in the registry.
